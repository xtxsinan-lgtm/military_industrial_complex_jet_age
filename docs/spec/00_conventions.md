# 00 — Conventions, Shared Contracts, and Spec Template

> Status: v1.2 (spine document — all module specs MUST conform). Owner: lead designer agent.
> Language: specs may be written in Chinese or English; **identifiers, schema keys, formulas, and code are always English**.

This document is the single source of truth for things that cross module boundaries. If a module spec needs to change anything here, it must NOT silently diverge — instead add an entry to its own "Cross-module change requests" section; the lead will reconcile and bump this file's version.

## 2. Repository layout (target)

```
docs/
  game_design.md            # high-level GDD (vision); specs below are authoritative on details
  spec/NN_<module>.md       # detailed module specs (this folder)
  validation/<topic>.md     # validation reports (generated by sim scripts + analysis)
  workplan/                 # ticket-level implementation plan (wave 4)
sim/                        # Python REFERENCE implementation (throwaway as product, permanent as oracle)
  mic/                      # package: aero/, engine/, perf/, econ/, procurement/, testing/, campaign/
  data/                     # JSON data shared with the game (copied verbatim into Godot project later)
  validation/               # scripts that produce docs/validation/*.md
  golden/                   # golden test vectors (JSON) consumed by C# unit tests
  tests/                    # pytest
.venv/                      # python venv (gitignored)
```

Python: 3.9 compatible (system python is 3.9.6). Allowed deps: numpy, scipy, matplotlib, pytest. Run with `.venv/bin/python`.

**The Python reference implementation is the oracle.** Every formula in a spec must exist in `sim/mic/...` and every spec must list golden vectors generated from it. C# implementation must reproduce golden vectors within stated tolerance (default rel 1e-6 for deterministic math, documented otherwise).

## 3. Units & numeric conventions

- Internal units: **SI** everywhere (m, kg, s, N, K, Pa, rad). Speeds in m/s internally, Mach where explicitly named `mach`.
- Display units for the US MVP: knots, feet, lb, lbf, nautical miles, ft/min, deg/s. Conversion only in UI layer (`Units` helper). Constants: ft = 0.3048 m; lb = 0.45359237 kg; lbf = 4.4482216152605 N; kt = 0.514444 m/s; nmi = 1852 m.
- Atmosphere: **ISA 1976** up to 25 km (`sim/mic/atmosphere.py`), owned by module 01.
- Angles: radians in code, degrees in data files when key name ends with `_deg`.
- Money: **then-year US dollars** (nominal), stored as `float64` dollars. Inflation index table in `data/economy/inflation_usd.json` (owned by module 04) for "constant-1950-dollar" displays.
- Randomness: all stochastic systems take an explicit deterministic `PCG32` stream from `sim.mic.rng.RngStreamRegistry` (keyed by FNV-1a 64 stream name hash; Module 09 specifies the bit-exact algorithm so Python and C# produce **identical streams**). Never use global random.
- Time: **simulation tick = 1 day**. Calendar is real-time-with-pause (Paradox-style), speeds 1–5. Most economic processes settle **monthly** (1st of month); projects progress daily. Date type = days since 1945-01-01 (int) + helper conversions.

## 4. Shared data contracts (authoritative top-level shapes)

Module owners fill in details; top-level keys below must not be renamed without a change request.

### 4.1 `Estimate` — every performance number the player sees carries uncertainty
```json
{ "value": 1.82, "sigma": 0.07, "source": "sim|tunnel|ground|flight|service", "unit": "mach" }
```
`value` = the player's current best estimate; the **true** value is hidden in `TrueAircraft` (module 06). `sigma` shrinks as better sources are used.

### 4.2 `AircraftDesign` (player-editable; owned by module 01, extended by 02/03/06)
```
AircraftDesign {
  id, name, company_id, created_date, role_tags[]           # e.g. ["day_fighter","carrier"]
  wing: WingGeometry                                        # area, aspect, sweep, taper, t/c, airfoil_ref, position, dihedral, devices[]
  fuselage: FuselageGeometry                                # length, max_diameter, area_ruled:bool, ...
  empennage: EmpennageGeometry                              # tail volume coeffs or explicit geometry; t_tail:bool
  intake: IntakeSpec                                        # type: nose|cheek|chin|wing_root; variable:bool
  propulsion: { engine_id, count, afterburner:bool }
  structure: { design_load_factor_g, material_mix{al,steel,ti}, carrier_capable:bool }
  fuel: { internal_kg }
  systems: { radar_id|null, fire_control_id|null, avionics_level }
  armament: { guns[], hardpoints:int, missile_ids[] }
  techs_used[]                                              # tech ids this design depends on (validated vs tech tree)
}
```

### 4.3 `EngineSpec` / engine deck (owned by module 02)
Callable contract: `engine.thrust_N(mach, alt_m, throttle∈[0,1], ab:bool)`, `engine.tsfc(mach, alt_m, throttle, ab)` [kg/(N·s)], plus static fields `mass_kg, diameter_m, length_m, unit_cost, mtbf_h, maint_mh_per_fh`.

### 4.4 `PerformanceReport` (output of module 01; input to 05/06/07 and the war system later)
Fixed key set (all values are `Estimate` when presented to player, raw float in `TrueAircraft`):
```
max_mach_sl, max_mach_alt, alt_of_max_mach_m, service_ceiling_m, climb_rate_sl_mps,
time_to_alt_10668m_s, sustained_turn_dps_m08_4572m, instantaneous_turn_dps_m08_4572m,
ps_mps_m09_4572m_1g, combat_radius_m (std profile, module 01 defines), ferry_range_m,
takeoff_distance_m, landing_distance_m, stall_speed_mps, max_load_factor_g,
empty_mass_kg, mtow_kg, internal_fuel_kg, payload_kg, thrust_to_weight_combat, wing_loading_combat_kgm2,
ps_grid (mach × alt grid, 1g, combat weight), 
unit_flyaway_cost_usd, dev_cost_usd_estimate, maint_mh_per_fh, carrier_suitability (bool + reasons)
```
`combat weight` = empty + 50% internal fuel + standard combat load (module 01 defines).

### 4.5 `Requirement` (military request for proposals; owned by module 05)
```
Requirement { id, program_name, name_key, customer: USAF|USN, role, mvp_core:bool,
  issue_date, proposal_due, first_flight_due, ioc_due,
  criteria: [ { key: <PerformanceReport key>, kind: threshold|objective|weighted, op: ">="|"<=", value, objective_value, weight } ],
  equipment: { carrier_capable, radar_required, min_crew, min_engines, internal_bay_required, min_guns_20mm, missile_capability },
  budget: { dev_usd, unit_price_ceiling_usd, quantity_planned },
  acquisition: { style: flyoff|paper_award|sole_source, contract_type_dev, contract_type_prod },
  eval_weights: { perf, cost, sched, risk },
  politics: { incumbent_bias{company_id: float}, congressional_interest: float },
  alt_history: { follow_on_to, suppress_if_mach_in_service },
  historical: { winner_company_id, winner_design_name, competitors[] } }
```

### 4.6 `CompanyState` (owned by module 04)
```
CompanyState { id, name, is_player, cash_usd, debt_usd,
  reputation{USAF,USN,export} (0..100, neutral 50), track_record (0..1, neutral 0.50), political_capital,
  engineers{aero,structures,propulsion,systems}, facilities{wind_tunnel_level, factory_floor_m2, test_site:bool},
  projects[], aircraft_in_production[], tech_unlocked[], tech_maturity{tech_id: float}, ... }
```

### 4.7 `HiddenFlaw` (owned by module 06)
```
HiddenFlaw { id, type, severity 1..5, trigger_condition, detect_prob_by_source{sim,tunnel,flight_test_item}, fix_cost_usd, fix_days, performance_penalty{key: delta} }
```

## 6. Spec template (every module spec MUST have these sections)

1. **Purpose & player fantasy** — what the player feels/decides here; which decisions are interesting and *why* (trade-offs).
2. **Scope** — MVP in / out.
3. **Player-facing flow** — step by step; what info is shown; what can go wrong.
4. **Data schemas** — exact fields, types, units, ranges, defaults. JSON examples.
5. **Algorithms** — exact formulas/pseudocode, every constant named, cited source (Raymer, Roskam, DATCOM, Mattingly, NACA reports, historical data) where applicable.
6. **Tunables table** — `name | default | range | effect | rationale`. All balance knobs live in `data/tuning/*.json`.
7. **Edge cases & failure modes** — invalid inputs, extreme designs, numerical stability, exploit risks.
8. **Golden test vectors** — reference to `sim/golden/<module>_*.json` (inputs → expected outputs, tolerance).
9. **Interactions** — inputs from / outputs to other modules (by contract name in §4).
10. **Validation results** — link to `docs/validation/...`, summary numbers.
11. **Open questions & cross-module change requests.**

Quality bar: "commercial game design doc" — a competent implementer should never have to invent a rule, number, string, or edge-case behaviour. If you had to decide something, **decide it and write it down** with rationale; list it under open questions only if it genuinely needs the user's taste.
